## Завдання 1. Видача решти

У файлі [task_1.py](task_1.py) реалізовано два алгоритми видачі решти для набору монет `[50, 25, 10, 5, 2, 1]`. Обидві функції приймають невід’ємну цілу суму та повертають словник, у якому ключі - номінали монет, а значення - їх кількість.

### Жадібний алгоритм

Функція `find_coins_greedy` перебирає номінали від найбільшого до найменшого. Для кожного номіналу вона за допомогою цілочисельного ділення визначає, скільки таких монет можна використати, та зменшує залишок суми.

Кількість ітерацій залежить від кількості номіналів, а не від кількості виданих монет: одна операція ділення одразу визначає кількість монет певного номіналу.

### Динамічне програмування

Функція `find_min_coins` послідовно знаходить мінімальну кількість монет для кожної проміжної суми від `0` до заданої суми. Масив `dp` зберігає ці мінімуми, а `coin_used` - монету, яка дозволила отримати відповідний мінімум. Після заповнення масивів функція відновлює набір монет для заданої суми.

Для суми `113` функції повертають:

```python
# Жадібний алгоритм
{50: 2, 10: 1, 2: 1, 1: 1}

# Динамічне програмування
{1: 1, 2: 1, 10: 1, 50: 2}
```

Обидва результати відповідають сумі `113` та містять п’ять монет. Відмінність у порядку ключів не впливає на результат: словники рівні.

### Теоретична складність

Позначимо суму через `S`, кількість номіналів - через `k`, а кількість монет у знайденому розв’язку - через `m`.

| Алгоритм | Часова складність | Пам’ять |
|---|---|---|
| Жадібний | `O(k)` | `O(k)` для словника результату; `O(1)` допоміжної пам’яті |
| Динамічне програмування | `O(S · k + m + k log k)` | `O(S + k)` |

Для ДП заповнення масивів займає `O(S · k)`, відновлення набору монет - `O(m)`, а сортування словника результату - не більше `O(k log k)`. Оскільки всі номінали - додатні цілі числа, `m ≤ S`.

Для заданих шести номіналів `k` є сталою. Тому часову складність жадібного алгоритму можна записати як `O(1)`, а ДП - як `O(S)`. Пам’ять жадібного алгоритму також стала, тоді як ДП потребує `O(S)` пам’яті. Ці оцінки використовують стандартне для такого аналізу припущення про сталу вартість арифметичних операцій.

### Порівняння часу виконання

Вимірювання проведено за допомогою `timeit` у Python 3.13 на сумах `113`, `1 000` та `10 000`. Для кожної суми кожну функцію викликано `1000` разів. Таблиця містить результати одного контрольного запуску, а не час одного виклику.

| Сума | Жадібний алгоритм, с / 1000 викликів | Динамічне програмування, с / 1000 викликів |
|---:|---:|---:|
| 113 | 0,0003 | 0,0346 |
| 1 000 | 0,0002 | 0,3626 |
| 10 000 | 0,0002 | 3,7882 |

Зі збільшенням суми від `1 000` до `10 000` час ДП зріс приблизно в `10,4` раза. Це узгоджується з лінійною залежністю часу від суми за незмінного набору номіналів. Час жадібного алгоритму залишився практично сталим, оскільки він у кожному випадку перебирає лише шість номіналів.

Час може коливатися між запусками через навантаження системи та роботу процесора. Для дуже коротких вимірювань також суттєве округлення до чотирьох знаків після коми. Тому менший час жадібного алгоритму для більшої суми в цій таблиці не є доказом його прискорення зі зростанням суми.

### Висновки

Для заданого набору номіналів жадібний алгоритм є ефективнішим за часом виконання та використанням пам’яті, особливо при великих сумах. Він одразу обчислює кількість монет кожного номіналу, тоді як ДП опрацьовує всі проміжні суми та зберігає для них додаткові дані.

Під час перевірки обох функцій на всіх сумах від `0` до `2 000` вони правильно відновлювали суму та повертали мінімальну кількість монет. Ця перевірка підтверджує результати на зазначеному діапазоні, але сама по собі не є доведенням оптимальності жадібного методу для всіх сум.

Перевага ДП полягає в гарантії мінімальної кількості монет для довільного набору додатних цілих номіналів, якщо задану суму можна скласти. Жадібний підхід загалом такої гарантії не має. Наприклад, для номіналів `[4, 3, 1]` та суми `6` він вибере `4 + 1 + 1`, а мінімальний розв’язок - `3 + 3`. Це приклад обмеження методу; у реалізації завдання використовується лише заданий набір `[50, 25, 10, 5, 2, 1]`.

Отже, для цієї касової системи жадібний алгоритм є практичним вибором для великих сум, а ДП демонструє підхід до пошуку гарантованого мінімуму ціною більших витрат часу та пам’яті.

## Завдання 2. Обчислення інтеграла методом Монте-Карло

У файлі [task_2.py](task_2.py) реалізовано обчислення визначеного інтеграла методом Монте-Карло та порівняння з аналітичним результатом і функцією `scipy.integrate.quad`.

Використано модель з опису домашнього завдання: `f(x) = x²` на відрізку `[0, 2]`. На цьому відрізку функція невід’ємна, тому інтеграл дорівнює площі під її графіком.

### Принцип обчислення

Область під графіком повністю міститься в прямокутнику з координатами `x ∈ [0, 2]` та `y ∈ [0, 4]`. Його висота дорівнює `f(2) = 4`, оскільки функція `x²` зростає на цьому відрізку. Площа прямокутника становить `(2 − 0) · 4 = 8`.

Алгоритм генерує `n` рівномірно розподілених псевдовипадкових точок у прямокутнику та рахує точки, для яких `y ≤ f(x)`. Частка таких точок наближає відношення площі під кривою до площі всього прямокутника:

```text
Оцінка інтеграла = 8 · (кількість точок під графіком / n).
```

Для обчислення використано `n = 100 000` та локальний генератор `random.Random(42)`. Фіксоване початкове значення `seed = 42` дозволяє відтворювати результат у тому самому середовищі, але не підвищує точність методу й не усуває похибку.

Часова складність обчислення - `O(n)`, допоміжна пам’ять - `O(1)`: точки обробляються послідовно, їхні координати не накопичуються в масиві.

### Аналітична перевірка

Первісна функції `x²` - це `x³/3`. За формулою Ньютона - Лейбніца:

```text
∫₀² x² dx = [x³/3]₀² = 2³/3 − 0³/3 = 8/3 ≈ 2,6666666667.
```

Додатково інтеграл обчислено через `scipy.integrate.quad(f, 0, 2)`. Це незалежна від випадкових точок чисельна перевірка; результат `quad` також є наближеним.

### Результати

Наведені значення отримано під час контрольного запуску `task_2.py` з `100 000` точок і `seed = 42`.

| Показник | Значення |
|---|---:|
| Метод Монте-Карло | 2,659680 |
| Аналітичний результат | 8/3 ≈ 2,666667 |
| Результат SciPy `quad` | 2,666667 |
| Оцінка абсолютної похибки самого `quad` | ≈2,96 · 10⁻¹⁴ |
| Абсолютне відхилення Монте-Карло від 8/3 | ≈0,006987 |
| Відносне відхилення Монте-Карло | ≈0,262% |

Абсолютне відхилення обчислено як `abs(mc_result − analytical)`, а відносне - як `abs(mc_result − analytical) / abs(analytical) · 100%`. Порівняння виконано до округлення чисел для друку.

Оцінка похибки, яку повертає `quad`, стосується лише його власного результату. Вона не описує похибку Монте-Карло та не є точно відомою помилкою `quad`. Збіг результату `quad` з аналітичним значенням до шести знаків після коми також не означає їх абсолютної математичної тотожності.

### Висновки

Алгоритм Монте-Карло отримав наближення `2,659680` до точного значення `8/3`. Відносне відхилення становить приблизно `0,262%`. Результат узгоджується з аналітичним обчисленням та перевіркою через `quad`, хоча поступається `quad` за точністю в цьому прикладі. Умова не встановлює конкретної допустимої похибки; отримане відхилення характеризує точність саме цього запуску.

Наявність відхилення очікувана, оскільки метод оцінює площу за скінченною випадковою вибіркою. У моделі незалежних рівномірних точок типовий масштаб похибки зменшується як `1/√n`: для його зменшення приблизно вдвічі потрібно приблизно вчетверо більше точок. Водночас для окремого запуску збільшення `n` не гарантує меншого фактичного відхилення.

Використання `f(b)` як висоти прямокутника правильне саме для обраної функції та відрізка. Для іншої функції або інших меж потрібно окремо перевірити, що функція невід’ємна та весь її графік на відрізку лежить у прямокутнику. Поточна реалізація розв’язує конкретний приклад із домашнього завдання.
